## Q1 — `eId` consistency

**Answer: yes, `eId` is present and universal across all three courts.**
Every body paragraph has `<paragraph eId="para_N">` and every section
heading has `<level eId="lvl_N">`. Values are sequential integers (`para_1`,
`para_2`, …, `lvl_1`, `lvl_2`, …) generated by TNA's transform pipeline,
not by the original court. They are verbatim-stable within a published
version — the navigator must return them unchanged, never compute its own.

### Elements carrying `eId`, counted across the three samples

```
UKSC 2019/41
    73 <paragraph
    10 <level
     2 <TLCRole
     2 <TLCPerson
     2 <TLCOrganization
     1 <TLCEvent

EWCA Civ 2024/1564
    78 <paragraph
    30 <level
     2 <TLCPerson
     2 <TLCOrganization
     1 <TLCRole
     1 <TLCEvent

EWHC Ch 2023/1234
   211 <paragraph
    20 <level
     9 <TLCPerson
     2 <TLCRole
     2 <TLCOrganization
     1 <TLCEvent
```

`TLC*` elements live in `<meta>` and are Akoma Ntoso "top-level
classification" references (parties, judges, roles). They have named `eId`s
like `ewca-civil`, `appellant`, `judge-lord-justice-warby` — **not** the
sequential `para_N` / `lvl_N` scheme. The TOC must filter them out: the
navigator only surfaces `paragraph` and `level` elements that live under
`judgmentBody`, not anything from `meta`.

### Edge: the author-attribution level has no `eId`

UKSC and EWHC both emit a leading `<level class="author">` just inside
`<decision>` that contains the author's name (e.g. "LADY HALE AND LORD REED
giving the judgment of the Court:") and **has no `eId` attribute at all**.
This is not a section; it's the pseudo-heading for the judge attribution.
The TOC builder should ignore any `<level>` without an `eId`.

## Q1b — Structural variation between courts (the real surprise)

**UKSC + EWCA Civ use a flat structure. EWHC Ch nests paragraphs inside
levels. The navigator parser must handle both.**

UKSC and EWCA Civ lay out `<decision>` as a flat sequence of siblings:

```xml
<judgmentBody>
  <decision>
    <level eId="lvl_1"><content><p>Introduction</p></content></level>
    <paragraph eId="para_1">…</paragraph>
    <paragraph eId="para_2">…</paragraph>
    <level eId="lvl_2"><content><p>Facts</p></content></level>
    <paragraph eId="para_3">…</paragraph>
    …
```

EWHC Ch nests paragraphs **inside** their level:

```xml
<judgmentBody>
  <decision>
    <level eId="lvl_1">
      <heading>Introduction</heading>
      <paragraph eId="para_1">…</paragraph>
      <paragraph eId="para_2">…</paragraph>
      <paragraph eId="para_3">…</paragraph>
    </level>
    <level eId="lvl_2">
      <heading>Facts</heading>
      …
```

### Implications for the parser

1. **Leaf lookup by `eId`:** use `//paragraph[@eId=$id]` or `//level[@eId=$id]` —
   an XPath descendant axis that works in both shapes. No XPath rewrites per
   court.
2. **TOC shape:** for each `<level eId="lvl_N">` emit a TOC entry; for each
   `<paragraph eId="para_N">` also emit one. The flat vs nested difference
   only affects **ordering and hierarchy display**, not addressability.
3. **Hierarchy (optional, v2):** if we want to show the LLM "paragraph 3 is
   under heading 'Facts'", we need one of:
   - Flat shape: walk siblings and associate each paragraph with the most
     recent preceding level.
   - Nested shape: take the XML parent chain directly.
   The simplest v1 is to emit a flat list of `{id, title, char_count}` and
   skip hierarchy. Ship the flat version first.
4. **`char_count` in the TOC:** for flat levels, `char_count` is just the
   level's own heading text (tiny, ~30 chars). For nested levels, it would
   include all descendant paragraphs (much larger). Document the semantics
   explicitly: `char_count` is the length of that specific element's text
   content, not "everything under it". If a caller wants "how big is this
   section including its paragraphs", they sum the children. Keeping this
   dumb makes the output identical across courts.

## Q2 — `eId` stability across republishes

**Partial answer: cannot verify without a same-doc diff across republishes,
but the FRBR dates prove republishes happen and give us a change marker.**

No hash or version field exists in the LegalDocML `FRBR` identification
block. Instead, TNA records three distinct dates:

```
UKSC 2019/41:
  FRBRdate date="2019-09-24"         name="judgment"      ← stable ruling date
  FRBRdate date="2025-03-31T10:55:46" name="transform"    ← XML transform
  FRBRdate date="2025-08-18T06:22:05" name="tna-enriched" ← enrichment pass

EWCA Civ 2024/1564:
  FRBRdate date="2024-12-13"         name="judgment"
  FRBRdate date="2024-12-13T10:37:31" name="transform"
  FRBRdate date="2025-07-19T04:37:51" name="tna-enriched"

EWHC Ch 2023/1234:
  FRBRdate date="2023-05-23"         name="judgment"
  FRBRdate date="2024-11-09T21:31:16" name="transform"
  FRBRdate date="2024-11-17T14:29:38" name="tna-enriched"
```

The important datum: **Miller II, a judgment from 2019, had its XML
transformed on 2025-03-31 and re-enriched on 2025-08-18.** TNA routinely
republishes old judgments. Any cache of section IDs held by a client across
days or weeks is therefore sitting on top of a moving target.

### Recommended mitigation

The navigator response must include the `transform` date, so:

- Clients holding cached `section_id`s can compare the transform date on
  their cached TOC against a fresh TOC and invalidate if it shifted.
- If a client passes a stale `section_id` to `get_section` and the leaf is
  missing, the tool can return a hint: "section not found — the judgment
  may have been republished; call `get_toc` to refresh."

Actually verifying `eId` stability across a specific republish would
require pulling the same judgment's XML from two points in time. TNA does
not expose version history publicly, so the only way to test this is to
cache XML locally now and diff against a future fetch. That work is
**not blocking** for Phase 3 — the mitigation above is sufficient as long
as clients are warned.

## Q3 — FastMCP 3.2.3 resource template syntax

**Confirmed. The `@mcp.resource("judgment://{court}/{year}/{number}")`
shape proposed in the pilot spec is the current idiomatic syntax.**

From the installed package at
`.venv/lib/python3.13/site-packages/fastmcp/server/server.py:1699-1711`:

```python
@server.resource("resource://{city}/weather")
def get_weather(city: str) -> str:
    return f"Weather for {city}"

@server.resource("resource://{city}/weather")
async def get_weather_with_context(city: str, ctx: Context) -> str:
    await ctx.info(f"Fetching weather for {city}")
    return f"Weather for {city}"

@server.resource("resource://{city}/weather")
async def get_weather(city: str) -> str:
    data = await fetch_weather(city)
    return f"Weather for {city}: {data}"
```

- Brace-style path params (`{court}`, `{year}`, `{number}`) are the wire
  format.
- Each brace param maps to a typed function parameter (`str`, `int`, etc.).
- `ctx: Context` is injected the same way tools get it — no special
  handling.
- Custom URI schemes are accepted; the decorator treats the URI as an
  opaque string. `judgment://…` will register without complaint.

No rewrite of the pilot spec is needed for this question.

## Q4 — Cache slot in `deps.py`

`src/deps.py:39-57` defines `http_lifespan` which yields:

```python
yield {"http": http, "xml_http": xml_http}
```

via `ctx.lifespan_context["http"]` and `ctx.lifespan_context["xml_http"]`.
Case law uses `xml_http` for TNA's XML endpoints.

**Phase 5 plan for the judgment cache:**

1. Add a third key to the yielded dict: `"judgment_cache": ...` — an
   in-memory mapping keyed by TNA slug, holding the parsed XML (or a
   lightweight `{"xml_bytes": ..., "fetched_at": ...}` entry).
2. Use `cachetools.TTLCache(maxsize=32, ttl=600)` — 10 minute TTL, 32
   judgments max. TNA updates infrequently and a single MCP session is
   unlikely to need more than a handful of judgments cached at once.
3. `get_toc` populates the cache on fetch; `get_section` reads from it and
   refetches only on miss.
4. No cache sync needed — cachetools is safe for single-process async.

The key architectural constraint from `CLAUDE.md` stands: "Gateway owns the
lifespan." The cache must be added to `http_lifespan` in `deps.py`, not
created inside the case_law module. All sub-modules inherit the full
`lifespan_context` dict; they don't own lifespan state independently.

## Bonus — `case_law_search` is broken in production, and it's worse than one bug

Out of scope for Phase 2 as originally framed, but the actual atom-feed
inspection done as pre-work for Phase 3 turned up a **two-bug finding
with a shared root cause**, not the single slug-source problem assumed
in the pilot spec.

### What the TNA Atom feed actually looks like today

Fetched on 2026-04-15:

```
curl -sS "https://caselaw.nationalarchives.gov.uk/atom.xml?query=negligence&court=uksc"
```

One representative `<entry>` (first result):

```xml
<entry xmlns="http://www.w3.org/2005/Atom"
       xmlns:tna="https://caselaw.nationalarchives.gov.uk">
  <title>THG Plc v Zedra Trust Company (Jersey) Ltd</title>
  <link href="https://caselaw.nationalarchives.gov.uk/uksc/2026/6" rel="alternate"/>
  <published>2026-02-25T00:00:00+00:00</published>
  <updated>2026-02-25T10:18:59+00:00</updated>
  <author><name>United Kingdom Supreme Court</name></author>
  <id>https://caselaw.nationalarchives.gov.uk/id/d-a5d0d664-cf93-4993-b257-ea7c752ad62b</id>
  <tna:contenthash>1db095d105462380be847343d93ed39c63ca8d84dfb913bd1c2ff124d5b3cc35</tna:contenthash>
  <link href="https://caselaw.nationalarchives.gov.uk/uksc/2026/6/data.xml"
        rel="alternate" type="application/akn+xml"/>
  <tna:identifier slug="uksc/2026/6" type="ukncn">[2026] UKSC 6</tna:identifier>
  <tna:identifier slug="tna.t7y2pv3m" type="fclid">t7y2pv3m</tna:identifier>
  <tna:uri>d-a5d0d664-cf93-4993-b257-ea7c752ad62b</tna:uri>
  <link href="https://assets.caselaw.nationalarchives.gov.uk/.../...pdf"
        rel="alternate" type="application/pdf"/>
</entry>
```

### Bug 1 — stale namespace URI

The current parser maps:

```python
"uk": "https://caselaw.nationalarchives.gov.uk/ns/properties"
```

TNA retired that namespace URI. The live feed uses `tna:` with namespace
URI `https://caselaw.nationalarchives.gov.uk` (no `/ns/properties`
suffix). Every lxml lookup of `uk:cite`, `uk:court`, or anything
`uk:`-prefixed silently returns zero hits. This is the root cause of the
"court field null" known issue that's been sitting around as "TNA Atom
feed doesn't emit court metadata" — it was never a TNA limitation,
always a parser bug.

### Bug 2 — atom:id is now an internal UUID, not the canonical slug

TNA now emits `<atom:id>` as `https://caselaw.nationalarchives.gov.uk/id/d-<uuid>`
— an internal document ID, not the canonical neutral-citation URL. The
parser strips `TNA_BASE/` and returns e.g.
`id/d-4f66195b-f378-4409-808d-919501779816` as the "URI slug", which then
fails to round-trip through `case_law_get_judgment` because that tool
builds the fetch URL as `f"{TNA_BASE}/{uri}/data.xml"` and TNA returns
404 for UUID-shaped paths.

### The fix — one element, one lookup

Both bugs collapse to a single patch in `_parse_atom_feed`:

1. Replace the `uk:` namespace entry with the correct `tna:` URI
   (`https://caselaw.nationalarchives.gov.uk`, no trailing path).
2. Source the slug from the `slug` **attribute** (not `.text`) of the
   `<tna:identifier type="ukncn">` element — the feed hands us the
   canonical slug verbatim, no URL-stripping required:

   ```python
   ident = entry.find('tna:identifier[@type="ukncn"]', ns)
   slug = ident.get("slug") if ident is not None else ""
   ```

3. Source the neutral citation (NCN) from the same element's `.text`
   (`[2026] UKSC 6`).
4. Source the court name from `<author><name>` (human-readable) or
   derive from the slug prefix if a slug-based enum is preferred.
5. Keep a fallback: if the `<tna:identifier>` is missing on an entry,
   fall back to the plain `<link rel="alternate">` (the one with no
   `type` attribute, whose `href` is the canonical URL) and strip
   `TNA_BASE/`. Log a warning so we notice if TNA rearranges again.

**Trap:** the slug lives in an **attribute**, not element text.
`ident.get("slug")` or `ident.attrib["slug"]`, never `ident.text` —
`.text` returns the NCN string, not the slug. The current code's
`raw_uri = uri_el.text.strip()` pattern is right for `atom:id` (whose
value is in text) and wrong for `tna:identifier` (whose slug is in an
attribute).

### Framing — this isn't a regression in our code, TNA changed the contract

Worth naming before the fix lands: the old parser was not "wrapped
weirdly" or doing anything obviously wrong. It was reading what TNA's
atom feed advertised at the time. TNA then changed two things:

1. `<atom:id>` was repurposed from a URL-shaped slug to an internal
   UUID. Arguably closer to RFC 4287 compliance (atom:id is supposed
   to be a permanent identifier, not a navigable URL) — the old
   parser's assumption that it contained a slug was always incidental
   to that spec, not a contract we could rely on.
2. The TNA namespace URI moved from
   `https://caselaw.nationalarchives.gov.uk/ns/properties` to the
   bare host `https://caselaw.nationalarchives.gov.uk`, and the
   conventional prefix renamed from `uk:` to `tna:`.

The new `<tna:identifier slug="uksc/2024/12" type="ukncn">` element
is TNA's **replacement contract** — a dedicated, explicitly labelled
attribute that carries the slug we actually wanted all along. Reading
`.get("slug")` off a typed element is materially harder to misuse
than "strip the base URL and hope," so the new parser code is more
robust than the old, not merely equivalent to it. This is adoption
of a better upstream contract, not a patch around an internal bug.

BAILII and any other legal-research tool parsing the same feed with
the same pattern is now silently broken in the same two ways. Not
our problem, but worth knowing when triaging anyone who says
"we used to be able to search UK case law and suddenly our tool
broke."

### Scope discipline

Phase 3 fixes only these two namespace-adjacent bugs in
`_parse_atom_feed`. No navigator code, no new tools, no doc-only edits
riding along. Any third issue the parser reveals waits for its own
scoped commit. Phase 4 begins from a clean parser baseline.

## What Phase 3 actually has to do

Phase 3 is scoped to the atom-feed parser only — **two bugs in
`_parse_atom_feed`**, shipped as one commit:

1. Map the `tna:` namespace correctly
   (`https://caselaw.nationalarchives.gov.uk`, no `/ns/properties`).
2. Extract the slug from `<tna:identifier type="ukncn">` via
   `.get("slug")`, not from `<atom:id>`.
3. Include a fallback to the plain `<link rel="alternate">` href if
   the `tna:identifier` element is missing on an entry.
4. Add harness scenarios so this regression is caught if TNA shifts
   again: one chained call (`case_law_search → case_law_get_judgment`
   fed by the search result) and one hardcoded-URI call
   (`case_law_get_judgment(uri="uksc/2019/41")`) as a stable reference.

Nothing else. No navigator code. No model additions beyond what the
parser itself needs.

## What Phase 4 inherits from this discovery

The navigator + leaf implementation (Phase 4) starts from a fixed parser
and can rely on these Phase 2 findings:

1. Parser can use XPath `//paragraph[@eId]` and `//level[@eId]` — works
   on both flat (UKSC / EWCA Civ) and nested (EWHC Ch) shapes.
2. Section ID format: echo `eId` verbatim from the XML. Never compute.
3. Filter `<level>` elements without `@eId` (author attribution).
4. Include the `transform` date from the FRBR block in the TOC
   response as a staleness marker.
5. `@mcp.resource("judgment://{court}/{year}/{number}")` with typed
   path params and `ctx: Context` injection is valid FastMCP 3.2.3
   syntax.

### Phase 4 open questions to test before the navigator merges

- **`char_count` semantics.** Flat vs nested levels need documented
  semantics. Pick "own text only" for v1, revisit if callers complain.
- **Fourth-court variety.** UKUT, FTT, and family courts (EWFC, EWCOP)
  have not been inspected in Phase 2. If any of them emit a third
  structural shape, the descendant-axis XPath assumption in point 1
  above needs re-verification. **Before merging the navigator, add a
  harness scenario that fetches one judgment from each of UKUT, FTT,
  EWFC, and EWCOP and asserts `_parse_judgment_toc` produces a
  non-empty TOC.** Belongs with the navigator code, not the parser fix.
- **Same-doc republish diff.** Out of scope for implementation, but
  recorded as a known gap mitigated by the `transform_date` field in
  the TOC response.

### Phase 5 note — caching dependency

`cachetools` is **not** currently a project dependency.
`pyproject.toml` lists fastmcp, mcp, httpx, pydantic, lxml — and
nothing else. When Phase 5 wires the judgment cache into
`deps.py:http_lifespan`, the choice is:

- Add `cachetools>=5.0` and use `TTLCache(maxsize=32, ttl=600)`, or
- Use a plain dict with a manual timestamp check (~15 lines for a
  32-entry, 10-minute-TTL, single-threaded async cache).

Recommendation: plain dict. 15 lines of code is not worth a new
dependency for this volume, and the manual TTL check is trivial in
the async context. Decision stays a Phase 5 call — not now.
